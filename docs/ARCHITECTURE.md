# Архитектура NSPUWidget: от виджета расписания к студенческому приложению

**Статус:** план поэтапного перехода, не утверждение об уже существующем API личного кабинета. Актуально для версии 2.4.

## Принципы

1. Расписание, объявления, аудитории и преподаватели — **публичные данные**. Они доступны без входа и должны работать офлайн благодаря локальному кэшу.
2. Пропуски («н-ки»), оценки, личные сведения и кабинет — **приватные данные**. Они должны быть доступны только после авторизации самого студента через официально поддерживаемый механизм НГПУ. Никаких паролей в GitHub, хардкода, логах, аналитике или обычных SharedPreferences.
3. **UI не парсит HTML и не управляет авторизацией.** Он работает с моделями/репозиториями; форматы данных и сетевые методы спрятаны за интерфейсами.
4. Каждый раздел независим: ошибка входа в кабинет не должна ломать расписание или виджеты.
5. Поддержка нескольких групп/семестров, устойчивость к изменению HTML и явные состояния загрузки/ошибки/устаревшего кэша.
6. Приватные данные нельзя автоматически отображать в домашнем виджете или уведомлениях, пока пользователь отдельно не разрешит показ на экране блокировки.

## Предлагаемая структура Gradle (по мере роста)

\`\`\`
:app                     // навигация, DI, настройки, общая Material 3 тема
:core:model              // учебная пара, дата, аудитория, преподаватель, оценка, пропуск
:core:network            // HTTP-клиент, ограничения времени, retry/backoff
:core:database           // Room: кэш, версии схем, индексы
:core:designsystem       // темы, типографика, компоненты карточек, Neon, AMOLED
:core:security           // Android Keystore, шифрование токенов, управление сессией
:data:public-schedule    // парсер НГПУ, реальные HTML-ссылки, репозиторий
:data:student-account    // только официально подтверждённый API/SSO
:feature:schedule        // дни/недели, список занятий и навигация
:feature:people          // расписание аудитории, преподавателя
:feature:announcements   // объявления и изменения
:feature:attendance      // н-ки и статистика посещаемости
:feature:grades          // оценки, зачёты и экзамены
:feature:account         // вход, выход, профиль, согласия
:feature:settings        // настройки приложения/виджета, обновления
:widget                  // системные RemoteViews, компактный/большой
\`\`\`

Не обязательно создавать сразу 15 модулей: для небольшого приложения сотни пустых модулей только замедлят сборку. На первом этапе достаточно **разделить пакеты и репозитории внутри текущего :app**, затем выделять самые тяжёлые/самостоятельные функции по одной.

## Модели и публичное расписание

\`\`\`kotlin
data class LessonId(val sourceGroupId: Int, val date: LocalDate, val slot: String)
data class TeacherRef(val id: Int, val displayName: String)
data class RoomRef(val id: Int, val displayName: String)
data class LessonDetail(
    val id: LessonId,
    val subject: String,
    val teacher: TeacherRef?,
    val room: RoomRef?,
    val kind: LessonKind
)
interface PublicScheduleRepository {
    suspend fun schedule(groupId: Int, date: LocalDate): List<LessonDetail>
    suspend fun refresh(groupId: Int): RefreshResult
}
\`\`\`

Начальная версия 2.4 использует лёгкий способ перехода: ссылки на \`teacher_shedule.php?id=...\` и \`room_shedule.php?id=...\` извлекаются из **реального HTML страницы группы**, сохраняются вместе с кэшем и открываются внешним браузером. Так не требуется второй сложный парсер расписаний. Позднее можно добавить встроенный общий экран публичного расписания для группы/преподавателя/аудитории, переиспользовав одну модель.

Текущий код приложения всё ещё использует \`Store\` и \`SiteParser\`. Их надо постепенно заменить на реализации интерфейсов и ViewModel; не стоит за один релиз переписывать рабочие сценарии.

## Личный кабинет, оценки и н-ки

**Прежде чем писать авторизацию, необходимо установить:**

- официальный адрес и поддерживаемый метод входа/SSO (OAuth2/OIDC с PKCE или другая одобренная университетом интеграция);
- действительно ли студенту разрешён программный доступ к собственным данным и имеются ли доступные endpoints;
- формат и смысл «н» (пропуск занятия, уважительный, отработанный), оценок/ведомостей и их частота обновления;
- разрешения, сроки хранения, процедура выхода и удаления локальных данных;
- требования университета и применимого законодательства к обработке персональных данных.

**Нельзя:** запрашивать логин/пароль НГПУ через самодельную форму, хранить их открыто, обходить CAPTCHA/SSO или парсить закрытые страницы без согласованной интеграции.

После согласования API используем системную авторизацию через браузер/Custom Tabs, PKCE, Android Keystore для защиты сессионных секретов, HTTPS, минимальные разрешения, локальную БД с удалением данных при выходе. Никаких внешних собственных серверов, пока это не потребуется и не появится отдельная политика данных.

## UX

Нижняя навигация не должна превращаться в 8 вкладок. Рекомендуем:

- **Расписание:** пары, аудитории, преподаватели, замены, окна.
- **Учёба:** оценки и н-ки с разделами внутри, только после входа.
- **Объявления:** общедоступная информация.
- **Профиль:** авторизация, выход, сведения кабинета.
- **Настройки:** тема, виджет, обновления, информация о приложении.

«Изменения» можно сделать фильтром/экраном внутри расписания вместо отдельной вкладки, чтобы освободить место в нижней панели.

## План внедрения

1. **2.4:** исправить возврат на предыдущий день; добавить переходы по официальным ссылкам преподавателей и аудиторий; регрессионные тесты; документ архитектуры. Никаких учётных данных.
2. **Следующий этап:** выделить UI состояния/репозитории, перейти с JSON SharedPreferences на Room для расписания и истории, добавить миграцию без потери данных. Настроить DI и ViewModel.
3. **Публичные карточки:** реализовать отдельные нативные экраны расписаний преподавателя и аудитории с тем же кэшем и механизмом обновления.
4. **Исследование кабинета:** проверить доступные официальные интерфейсы/документацию/полномочия интеграции, получить согласованный сценарий входа. Не запускать реальную интеграцию, пока эти детали не подтверждены.
5. **Учёба:** защищённые оценки и посещаемость только после подтверждённой интеграции; обособленные уведомления с настройкой приватности.
6. **Дополнительно:** избранные аудитории/преподаватели, история изменений, экспорт пар в календарь, локальные напоминания; эти возможности не требуют личного кабинета.

## Проверки качества

- unit-тесты переходов дат, парсинга официальных ссылок и соответствия расписания;
- интеграционные тесты HTML фикстур нескольких групп/недель;
- эмулятор: свайпы, стрелки виджета, состояние после полуночи, офлайн, смена группы, тёмная/светлая темы;
- без утечек токенов в логи, без вызовов сети в UI и повторного парсинга HTML при прокрутке.
